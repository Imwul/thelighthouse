**Date:** 2026-10-08 (Asia/Seoul)
**Problem Solver:** Codex, BMAD Creative Intelligence Suite

## 🎯 PROBLEM DEFINITION

### Initial Problem Statement

사용자는 기존 웹앱을 처음부터 재검토하고 실제 플레이에 더 빠르고 자연스러운 도구로 직접 수정하라고 요청했다. 기존 기능·배치·디자인 결정은 제약으로 보존할 필요가 없다.

### Refined Problem Statement

등대지기가 날씨·점등을 시작하고 임무 선택→판정→서술→다음 선택을 반복하는 동안, 제품의 정보구조·상태·규칙 해석이 실제 절차를 끊지 않아야 한다. 선택 확장의 기능 목록보다 반복 업무와 기록을 우선하고 원문의 열린 해석을 보존해야 한다.

### Problem Context

- 기본 루프 p.5: 시작은 한 번, 밤의 임무는 원하는 만큼 반복, 만족하면 마무리.
- p.35–38: 날짜/시간, 감정에 의한 날씨 선택, 앞면+빨강 동시 점등, 태엽 감기.
- p.42–47: 정비/관찰은 d6와 카드, 사건은 카드 값과 색;9/K가 루프를 바꿈.
- p.48–49: 자율 소등, 분위기별1–4회 덱 셔플, 마지막 소감.
- p.51–67: 선택 미니게임·계절은 독립 절차와 여러 밤에 걸친 자료를 가짐.
- p.7–8: 플레이북은 서술용이며 판정 보정이 아님.

### Success Criteria

1. 원문의 필수 순서·예외·표·기간·한밤 한응답 제약을 올바르게 구현.
2. 현재 결과를 확인하고 자신의 글로 기록한 뒤 다음 임무를 쉽게 선택.
3. 작성 중 상태와 지난 기록·보관물·계절·덱을 안정적으로 보존.
4. 모바일/데스크톱에서 필요한 정보가 잘리지 않고 같은 개념으로 사용 가능.
5. 시각 위계가 실제 플레이 빈도와 다음 행동을 드러냄.

### Root Cause Analysis

**Five Whys 가설**:

1. 플레이 중 왜 멈추는가? 당장 필요한 판정/규칙/기록/다음 행동이 서로 멀거나 상태가 불명확할 수 있다.
2. 왜 서로 멀어지는가? 개별 기능이나 챕터를 페이지 단위로 배치하면 실제 사용 빈도와 순서가 반영되지 않는다.
3. 왜 원문과 다른 우선순위가 생기는가? 기존앱의 기능 목록을 룰북의 해석 틀로 삼으면 핵심 반복과 선택 확장을 같은 층위로 취급한다.
4. 왜 이를 바로잡기 어려운가? 기존 레이아웃을 제약으로 유지하면 작은 개선만 하고 루프의 구조를 바꾸지 못한다.
5. 무엇을 바꿔야 하는가? 룰북을 먼저 독립 추출하고 **현재 밤의 과제와 기록**을 제품의 주 단위로 다시 잡는다.

이 사슬은 현재앱 실제 감사에서 확인·반박할 진단 가설이다. 개발자의 의도나 과거 결정 이유를 사실로 주장하지 않는다.

|---|---|---|

이 표는 정적 코드 감사이며 실제 참가자의 행동/체감 보고가 아니다. 변경 전 App.jsx 주요 위치는 시작76/1300+, 점등563, 임무638–674/1950–2090, 종료814/2133, K2030, 물건2078–2090, 계절473–495/529, 덱463, 초안/백업431–458이다. 현재 코드 줄번호는 재설계로 달라질 수 있다. 브라우저 실제 과제의 조작수·화면 검증은 구현 후 결과로 별도 기록한다.

### Contributing Factors

Fishbone 관점에서 잠재 원인은 절차(시작/반복/끝의 혼합), 정보(결과 해석의 분리), 도구(덱/실물 입력), 저장(대기 임무/글의 연속성), 환경(밤의 피로·모바일), 시각(선택 확장과 핵심의 동등 강조)이다. 각 항목은 구현 후 과제 검증으로 확인해야 한다.

### System Dynamics

규칙을 찾으려고 이동 → 현재 결과/글을 기억해야 함 → 작업 맥락이 약해짐 → 글쓰기 지연 → 기능만 클릭하는 경험으로 변질될 수 있다. 이를 끊는 지점은 **선택한 임무 하나의 결과·규칙·기록·다음 선택을 연결**하는 것이다.

선택 확장의 상시 노출 → 첫 화면 읽을 양 증가 → 시작 지연 → 핵심 플레이 이해 지연의 가능성도 있다. 대신 필수 루프를 먼저 보이고 확장을 필요할 때 열 수 있게 한다.

## 📊 ANALYSIS

### Force Field Analysis

**Driving Forces (Supporting Solution):**

- 사용자가 정보구조·레이아웃·디자인 전면 변경과 코드 구현을 명확히 허용.
- 완전판 룰북과 로그북이 프로젝트에 제공됨.
- 솔로 로컬 웹앱은 세션 상태를 중심으로 단순한 흐름을 설계하기에 적합.
- 원문 자체의 기본 루프와 판정 도구가 명료하여 정확한 대조 가능.

**Restraining Forces (Blocking Solution):**

- 기존 저장 데이터와 현재 사용법의 연속성.
- 선택 확장의 서로 다른 상태/주기(밤/날짜/여러 세션).
- 덱·점등·대기 임무·기록을 묶는 저장 일관성.
- 원문의 미정 사항을 앱이 편의상 지나치게 단정할 위험.
- 실제 참가자의 서술 몰입·이해 정도는 이번 대리 검증으로 확정할 수 없음.

### Constraint Identification

실제 제약: 제공된 규칙, 현재 프로젝트 기술 환경, 브라우저 저장 안정성, 모바일 공간, 작성한 기록의 보존. 가정에 불과한 제약: 기존 메뉴명/배치, 모든 기능 상시 노출, 시작 전 플레이북·계절 필수 선택, 새 디자인이 기존 기능을 그대로 따라야 함.

일차 병목은 게임 전체 문헌을 읽는 속도가 아니라 **판정된 한 임무를 자신의 기록으로 만든 뒤 다음 임무로 넘어가는 연결**이다.

### Key Insights

- 상태가 있는 밤 플레이 도구가 규칙 카탈로그보다 기본 루프에 맞는다.
- 새 디자인은 단계의 명료함과 자유 반복을 함께 가져야 한다.
- 판정 결과는 자동 완성된 이야기나 성공/실패 점수로 환원하지 않는다.
- 연속성을 가진 항목(글, 덱, 보관물, 대화, 계절)은 실제 상태로 저장해야 한다.

## 💡 SOLUTION GENERATION

### Methods Used

Assumption Busting으로 기존 UI 보존 가정을 없애고, Morphological Analysis로 내비게이션/작업 맥락/판정/기록/확장을 조합했다. SCAMPER와 Reverse Brainstorming으로 맥락을 끊는 배치를 찾아 뒤집었다.

### Generated Solutions

1. “오늘 밤”을 기본 작업 시작점으로 사용.
2. 진행 중 밤 이어가기와 새로운 밤 시작을 구분.
3. 임무3종을 동등한 핵심 선택으로 배치.
4. d6→카드의 결과를 같은 임무 공간에서 순차 제공.
5. 카드 값·문양·색의 의미를 결과와 함께 표시.
6. 자신의 글을 입력하는 대기 임무를 하나만 유지.
7. 모든 작성 중 글과 판정 상태를 자동 저장.
8. 실물 도구 결과를 직접 입력하는 동등한 흐름 제공.
9. 점등 실패 반복과 성공 후 태엽을 분리.
10. 사건9/K가 마무리/재시작 절차를 안내하고 기록 보존.
11. 종료에서 소등·셔플·최종 소감을 묶음.
12. 보관물·미니게임·계절·등대지기를 맥락 드로어로 이동.
13. 수집은 한 카드→동전→해석/보관을 순차 실행.
14. 빛과의 대화는 질문·두동전·응답·한밤1회·이력을 연결.
15. 계절 누적/다음날/기간/종료 초기화를 구분.
16. 참고 화면은 판정별 짧은 규칙과 원문 페이지로 찾기 쉽게 제공.
17. 모바일 단일 작업 흐름, 데스크톱 여유는 기록과 참고 배치에 사용.
18. 저장 자료 내보내기/가져오기와 이전 기록 열람을 제공.

### Creative Alternatives

- 모든 규칙이 보이는 조회 대시보드.
- 전체 밤이 순서대로 진행되는 안내 위저드.
- 세션 책상에 핵심 루프를 두고 보조 도구를 꺼내는 구성.

각 대안은 Design Thinking 문서에 명료한 사용 여정과 장단점을 기록했다.

조회형은 필수 절차와 기록이 약하다. 위저드는 시작에는 좋지만 임무 자유 반복·재점등·선택 도구·K재시작이 경직될 위험이 있다. 세션 책상은 더 많은 상태 구현이 필요하지만 정확성과 반복 작업에 가장 적합하다.

### Recommended Solution

## 📝 LESSONS LEARNED

### Key Learnings

룰북 자체에서 시작/반복/끝의 정보구조를 추출하면 기존앱의 메뉴에 얽매이지 않고 판단할 수 있다. 정비는 단순 성공판정이 아니며, 날씨는 감정에 의한 선택이고, 선택 확장에는 별도 시간/횟수 규칙이 있다. 각 미묘한 차이는 화면보다 상태와 문구에 영향을 준다.

### What Worked

원문 전체 독립 검토, 구현을 보지 않은 규칙 분석과 별도의 사용자 과제 감사, 세 가지 대안의 비교, 규칙/루프 우선의 평가, 실제 코드·저장·브라우저 검증으로 이어지는 계획.

### What to Avoid

읽지 않은 원문을 기존 데이터로 대체하기, 장식만 바꾸기, 필수 플레이북/계절 설정 발명, 임의 반올림/코인상태 대응을 원문 규칙으로 주장하기, 경험적 증거 없이 속도/만족도 개선 수치 주장하기, 기록을 삭제하는 재시작.
