# Problem Solving Session: 기록의 무결성과 참조 흐름의 마지막 결함

**Date:** 2026-10-21
**Problem Solver:** Codex
**Problem Category:** 데이터 연속성·사용성·배포 재현성

## PROBLEM DEFINITION

**Initial Problem:** 최종 품질 감수를 통해 실제 사용성과 고유한 디자인을 개선하고 검증·push한다.

**Refined Problem:** 정상 플레이 검사는 통과하지만 예외 입력과 구형 자료, 저장 용량 오류, 찾기 실패에서 기록을 구분하거나 작업 맥락을 유지하지 못한다. 별도로 잠금 파일이 임시 경로에 의존해 새 설치가 실패한다.

**Context:** 로그인 없는 localStorage 기반 한국어 솔로 저널링 앱. React·Vite와 game.js의 순수 규칙 로직, 네이티브 dialog, 지연 로드 Firebase가 있다. 데이터와 원작의 절차, 기존 디자인을 보존한다.

**Success Criteria:** 읽은 글과 구형 기록을 잃지 않고 개별 조작한다. 본문 단어로 규칙을 찾는다. 참조 후 도구의 초안으로 돌아간다. 설치·테스트·린트·빌드와 실제 UI 검사에 통과한다.

## DIAGNOSIS AND ROOT CAUSE ANALYSIS

`bmad-cis-problem-solving`의 SKILL.md·customize.toml·solving-methods.csv·template.md를 읽고 활성 설정을 해석했다. 추가 지시가 없음을 확인했다. 사용자 요청에 따라 대화형 중간 승인을 생략했다.

**Methods:** Problem Statement Refinement, Is/Is Not Analysis, Five Whys, Systems Thinking.

| 경계 | 문제가 있는 곳 | 정상인 곳 |
|---|---|---|
| 기록 식별 | ID 누락·중복의 구형 일지/소지품/대화 | 새로 생성한 UUID 기록 |
| 저장 | 정규화 후 보조 백업 쓰기가 실패한 초기화 | 충분한 저장 공간에서 시작 |
| 검색 | 규칙 본문 단어·다중 공백·일지 0건 | 미리 등록한 주제/키워드 |
| 전환 | 도구에서 규칙 열기·판정 방식 변경 | 기본 밤의 단계 전환 |
| 설치 | 임시 경로로 기록된 lock 패키지 키 | 기존 머신의 node_modules |

**Five Whys:**
- 여러 일지가 함께 열리고 삭제된다 → undefined/중복 id로 비교한다 → 가져오기가 해당 ID를 허용한다 → 데이터 경계가 렌더링과 편집의 식별 요구를 보장하지 않는다 → 종전 검사는 ID가 있는 한 개의 구형 일지만 가져왔다.
- 읽은 글이 기본값으로 바뀐다 → 초기 정규화 try 블록 전체가 실패한다 → 보조 원본 백업 setItem이 용량 오류를 낸다 → 읽기·변환·보조 쓰기를 하나의 실패 경계에 넣었다 → 쓰기 실패에서 메모리 데이터 보존을 검사하지 않았다.
- 본문 검색이 안 된다 → 주제/수동 키워드만 검색한다 → 화면 콘텐츠와 검색 색인이 분리되어 있다. 키워드 추가만으로는 같은 누락이 반복된다.
- 새 설치가 안 된다 → lock의 모든 package 키가 `../../private/tmp/lighthouse-runtime/node_modules/` 아래다 → 임시 실행 환경에서 작성한 lock이 저장소에 들어왔다. 기존 패키지 버전·integrity를 유지하고 키만 정상화해야 한다.

**Systems Thinking:** 백업 검증 결과 → 앱 초기 데이터 → React key/개별 동작 → 저장/재복원으로 이어진다. 경계에서 안정적인 ID를 제공하면 여러 화면의 같은 오류를 함께 해결한다. 화면에 표시할 규칙 트리를 색인에도 사용하면 문서와 검색이 같이 갱신된다.

## ANALYSIS

**Driving Forces:** 기존 순수 로직과 브라우저 테스트, 원본 백업 보존 구조, 프로젝트의 명확한 시각 정체성.

**Restraining Forces:** 단일 App 파일의 큰 규모, localStorage 용량·브라우저 권한, 외부 계정과 네트워크, 실제 참가자 부재.

**Constraint Identification:** 데이터 보존과 사용자 요청 범위. 전체 상태 관리/백엔드/디자인 개편은 필요하지 않다. 취향이 불명확한 선택은 보존한다.

## SOLUTION GENERATION

**Methods:** SCAMPER for Problems, Assumption Busting, Failure Mode Analysis.

검토한 12개 해결안: (1) 배열 인덱스로 조작, (2) 데이터 경계 ID 보완, (3) 구형 데이터 거부, (4) 쓰기 실패 시 기본값, (5) 정규화 결과와 보조 쓰기 분리, (6) IndexedDB 전면 이전, (7) 수동 검색 키워드 추가, (8) 표시 트리 기반 색인, (9) 도구 복귀 버튼, (10) 모든 참조를 새 창, (11) 일지 행/규칙 탭 편집, (12) 새 공통 카드 디자인으로 전체 교체.

**Creative Alternatives:** 서버 검색·완전한 오프라인 동기화·모든 기록 자동 클라우드 동기화도 고려할 수 있으나 이번 결함과 직접 비례하지 않고 새 위험과 운영 부담을 만든다.

## LESSONS LEARNED

정상 흐름의 성공은 데이터 경계의 완성도를 보장하지 않는다. 수치상 overflow가 없어도 긴 제목이 목록을 지배하면 읽기 UX는 실패한다. 성공적인 청색 등대 장면과 종이 기록 면을 보존하면서 기록·참조 역할에 맞는 밀도를 다듬는 것이 전체 리디자인보다 목표에 적합하다.
